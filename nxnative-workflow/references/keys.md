# 密钥获取与检查

入口：`$nxnative-workflow 准备游戏与密钥`。

`prod.keys` 是系统级密钥集合，通常供多款游戏使用；是否适用取决于其中是否包含游戏所需的密钥代际。游戏专属的 title key 是另一层概念；nxnative 的 `dm/tools/nx_extract` 会尝试导入 NSP 票据。先读取当前 `nxnative/docs/agents/01-extract.md` 的密钥说明，以实际提取结果判断兼容性。

## 来源与下载

优先使用用户提供的本地文件。用户要求从网站下载时，本工作区指定来源为 <https://prodkeys.one/>；下载不属于初始化源码 submodule 的步骤。

本工作区实际走通的入口为：首页 → `/ryujinx-prod-keys/` → `/download/`。页面按模拟器命名，不代表存在 nxnative 专用密钥版本。重新读取当前页面中的版本和实际文件链接，不将已观察到的版本当作永远最新。

下载页可能显示 WordPress 密码表单。读取详情页公开提供的口令，通过页面声明的 `wp-login.php?action=postpass` 表单正常提交，并使用本次操作的 cookie jar 跟随跳转，再提取解锁页面中的文件链接。不要猜测口令或绕过访问控制；没有公开口令且用户未提供时，说明所缺信息。

网页读取工具曾返回 403，而经允许的本机 `curl` 请求返回 200；这可能涉及不同访问来源的过滤，具体机制未确认。分别记录每种访问方式的结果。HTTP 200 仍可能是口令页，不能直接当作 ZIP 下载成功。不要关闭 TLS 验证或运行网页要求下载的程序。

## 保存与检查

- 本工作区用户指定将密钥、下载 ZIP、cookie jar 与原始文件保存在 Git 忽略的 `games/` 下。已有游戏构建目录时保存在该目录中；游戏尚未确定时使用 `games/_downloads/keys/`。不要写入受 Git 追踪的文件，也不要将长期资料仅留在系统临时目录。
- 限制下载和解压大小，检查实际 ZIP 内容。只按名称读取唯一的 `prod.keys`，不要直接 `extractall` 或使用归档提供的路径写文件。包内附带的 `title.keys` 不自动作为当前游戏的输入。
- 检查文本中非空、非注释行是否为 `name = hexadecimal`，是否存在重复名称或异常长度。输出名称、条目数量、异常数量与摘要即可，不输出密钥值。
- nxnative 的提取说明记录过 33 条错误长度的 `*master_kek_source_*`。遇到此类条目，按该类型应为 16 字节检查；保留完整原件后，再在独立副本中删除错误长度行。不要截断、补齐或猜测值；其他未知异常先调查。
- 输出文件使用仅当前用户可读写的权限，保留候选来源、页面标注版本及文件 SHA-256。网站版本标注与格式检查不能证明密钥值正确，也不能证明适合目标游戏。

## 接入提取流程

确认游戏目录及目标版本后，将整理后的文件路径传给构建脚本的 `-k` 参数。在提取阶段检查是否缺少所需密钥、能否读取游戏元数据及模块，并记录实际结果。下载失败、格式失败与游戏提取失败应分别报告。

未取得游戏输入时，只能报告“候选文件已下载并完成格式检查，实际提取尚未验证”。不要为了测试密钥而自动发起完整 IPA 构建。
