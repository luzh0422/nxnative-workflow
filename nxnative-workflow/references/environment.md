# 环境初始化

入口：`$nxnative-workflow 初始化环境`。

目标是准备基础仓指定版本的源码并检查工具链。本次调用初始化 `nxnative` 与 `LiveContainer` 两个子仓；日常任务自动准备依赖时可仅处理实际需要的子仓。不要下载游戏或询问密钥内容。

## 1. 确认基础仓与锁定版本

先解析发现入口的符号链接，定位真实 Skill 目录的上一级目录，确认它本身就是 Git 工作区根目录，不能误用 `.agents/skills/`、父目录或现有 nxnative 子仓的 Git 状态。

读取 `.gitmodules`，核对两个路径和 URL；用 `git ls-tree HEAD -- nxnative LiveContainer` 确认基础仓提交中两个路径均是 `160000` gitlink，记录其完整 commit ID。比较暂存区是否存在尚未提交的依赖指针或 `.gitmodules` 变更；若有，先报告并保留，避免自行决定采用哪个版本。

如果基础仓未初始化、没有可读取的 HEAD 或缺少 gitlink，报告“基础仓尚未完成注册”，参照基础仓 README 给出所缺的维护步骤。此时不能声称依赖初始化成功，也不自动执行 `git init`、`submodule add`、提交或创建新的依赖指针。文件夹和 `.gitmodules` 存在不代表 submodule 已注册。

## 2. 检查已有工作现场

对于已经初始化的子仓，读取其适用指令，检查工作区、暂存区、未跟踪文件及嵌套子仓状态。记录实际 HEAD 与基础仓锁定 commit 是否一致。

如果存在本地修改、尚未推送的提交、正在进行的 merge/rebase，或切换版本会离开用户正在工作的分支，保留该子仓，报告路径、差异及影响。不能自动 stash、reset、clean、强制 checkout 或覆盖现有文件。无法确认已有提交是否有保留位置时，不自动切换它。可继续检查其他独立依赖和工具链，最终标明哪些项目仍待处理。

已有子仓的 remote 与 `.gitmodules` 不同，先报告；不要用 `sync` 或修改 remote 静默覆盖用户的 fork 配置。

## 3. 初始化并核对

确认目标子仓可以安全初始化或同步后，从基础仓根目录逐个执行：

```sh
git submodule update --init --recursive --checkout -- nxnative
git submodule update --init --recursive --checkout -- LiveContainer
```

只执行本次实际需要且检查通过的命令。已在目标 commit 的子仓无需再次 checkout，避免改变现有分支状态；仍需检查其嵌套依赖是否就绪。

使用基础仓记录的 commit；不要使用 `--remote`、子仓 `git pull` 或自动拉取基础仓新版本。需要的新对象可以由 `update` 获取。递归更新同样需要保留嵌套子仓的开发现场。

命令失败时保留现有状态并报告退出状态与原因；权限或网络阻塞时给出可在本地执行的准确命令，不反复重试同一失败，不以重新克隆或删除目录绕过问题。

完成后用 `git submodule status --recursive` 及各子仓实际 HEAD 核对版本。确认本次操作没有改变基础仓的 gitlink 指针；只有目标路径及其需要的嵌套依赖均就绪才能报告源码初始化完成。

## 4. 检查构建工具

读取两个子仓当前版本的构建说明，按实际移植路径检查平台架构、Git、Python、Xcode 与 SDK、依赖命令及 Python 模块是否可用；具体版本要求以所检出的源码为准。仅列出已检查项目及证据，不凭工具文件存在就认为 SDK 或目标平台可构建。

此调用执行检查，缺失工具则提供安装建议。软件安装、Xcode 下载、签名配置、游戏构建及设备安装不自动包含在此次初始化中；已有会话另行授权的操作按已有范围继续。

## 5. 输出与续接

汇报基础仓 revision、每个子仓的锁定/实际 revision、初始化结果、工具链缺项和下一步。明确区分“源码就绪”“工具链检查通过”“尚未验证构建”。更新 [进度记录](progress.md)，不把当前机器的限制固化为其他使用者的环境要求。
